# 个人微信自动回复 Agent 测试驱动开发方案

本方案定义测试契约、31 组离线场景、红绿重构批次和 8 项真实微信验收。它是待实现行为的依据，不是测试通过记录。项目当前事实以源码、实际命令输出和 `docs/tdd-progress.md` 为准。

## 一、目标与范围

交付可运行、可测试、可演示的 macOS 个人微信私聊文本自动回复 MVP。优先确保不误发、不重复发送、不串联系人记忆、不在未知状态下继续发送。语音、文件处理和 LLM 摘要本阶段不实现。

- 仅处理私聊；群消息跳过并记录，被 @ 仅进入人工队列。
- 默认 dry-run；人工确认与白名单 auto 由用户明确选择。
- 最高优先级待出题方确认：允许的接入方式及目标版本。其他待确认项为账号角色、运行模式与截止日期。
- 默认采用经授权的 Accessibility UI 自动化，不读取或解密微信数据库，不提取凭证，不 hook、注入或使用失效网页版协议。
- 真实开发、测试和演示只使用备用测试小号，优先文件传输助手或双小号互发。
- 接手时重新检查接口、测试、入口、FAQ、schema 与真实验收记录，不能把历史脚手架检查结论当作当前事实。

## 二、TDD 执行规则

每次只选择一个可观察行为，完成一个红绿重构循环，再推进下一行为。

| 阶段 | 必须做的事 | 完成证据 |
| --- | --- | --- |
| 红灯 | 新增一个有明确输入、动作和断言的测试；运行并确认因目标行为缺失而失败 | 测试名称、命令、失败原因 |
| 绿灯 | 只补足使当前行为成立的最小实现；运行当前测试和受影响测试 | 测试通过、退出码 0 |
| 重构 | 消除重复、收敛接口或依赖；不改变已定义的外部行为 | 受影响测试仍通过 |
| 批次验收 | 运行该批次集成测试；触及共享状态、发送或持久化时运行完整离线回归 | 实际结果与剩余问题 |

环境缺依赖、语法错误、测试未收集，不算有效红灯。首次接口尚未创建时，可以用目标接口缺失证明红灯；接口建立后应优先让测试失败于行为断言。

不为占位文件、单纯 getter 或与实现逐行对应的代码编写测试。优先测试发送次数、状态变化、队列内容、记忆隔离和用户能看到的输出。覆盖率仅用于查漏，不以覆盖率数字代替验收行为。

### 2.1 确定性与隔离

- 所有自动化测试中的 LLM 全部 mock，不读取真实 API 密钥，不向真实模型服务发请求。
- 使用固定时钟、可推进的虚拟时间、固定输入和临时 SQLite；不靠真实等待或随机输出断言。
- 顺序和并发用事件、屏障或可控任务验证，不用“睡眠一秒应该结束”的断言。
- Mock 微信适配器记录 receive、send、status、readback 调用，能够模拟错误窗口、不可用、发送失败和读回未知。
- 单元、集成和 CLI 测试禁止触达真实微信；真实验收由单独流程执行，不能混入默认 pytest。
- 测试数据全部虚构；测试数据库、日志、截图和私聊不写入源码目录或提交。
- pytest 收集结果必须大于零；关键清单中的场景不得以 skip 或 xfail 冒充完成。

## 三、先确定测试契约

以下是待实现的行为约定，不代表现有项目已提供这些接口。

### 3.1 消息、时钟与适配器

统一消息至少包含合成消息 ID、会话 ID、发送者、方向、消息时间、类型、文本、是否群聊和是否被 @。明确区分消息时间与本轮观察时间。

适配器以 receive、send、status、readback 四类操作表达收消息、尝试发送、检查可用性和重读当前窗口。测试使用相同行为契约约束 Mock 与 AX 适配器；具体同步或异步签名在第一批次固定。

合成 ID 使用会话 ID、发送者、文本和时间桶的哈希。相同消息的重复观察须保持分桶依据稳定，不得每轮按当前轮询时刻重新分桶。UI 时间不足时，以稳定的首见观察信息维持当前可识别消息的身份；无法区分的同桶相同消息保留已知限制，不在 MVP 中承诺完美解决。

滑动去重窗按观察时间淘汰缓存。窗口失效、重启或快照重建时不能擅自把历史消息当作待补发消息。UI 本身无法保证消息无遗漏或完整历史身份，这一限制须进入 README。

### 3.2 发送和会话状态

发送模式与会话状态分开：模式为 dry_run、confirm、auto；会话状态至少区分运行、暂停、人工接管、熔断、发送未知。

| 条件 | 必须观察到的行为 |
| --- | --- |
| dry-run | 仅预览，适配器 send 调用为 0 |
| confirm 未批准或已拒绝 | 不发送；被 @ 群消息仍只作人工处理 |
| confirm 已批准 | 发送前重新检查模式、会话、窗口和暂停状态，避免批准后条件变化造成误发 |
| auto | 只有显式启用且通过白名单、过滤、状态、限速和配额检查的私聊才能尝试发送 |
| 已尝试发送且读回确认 | 仅记为本地发送成功，不声明对方送达或已读 |
| 已尝试发送但读回未确认 | 记为未知，暂停该会话，进入人工核查，不自动重试 |
| 暂停、人工接管或熔断 | 后续消息不能触发自动发送 |
| 重启 | 保留暂停、熔断和未知等限制状态；不能自动补发积压或历史预览 |

读回必须核对目标会话、本次发送后的新增己方文本。发送前已有的一条同文本消息不能当作本次成功证据；无法可靠关联时返回未知。

### 3.3 配额和连续回复

每会话每小时上限按滑动一小时窗口计算，边界采用“距当前时间小于一小时”的记录。连续上限按连续自动发送次数计算，不因又收到一条对方消息就重置，避免两个机器人互答绕过限制。

一次成功占用一次自动回复名额；已尝试但结果未知也保留名额并暂停。发送前原子预留名额，防止并发请求同时通过最后一个名额。能够确定尚未产生发送动作的失败才释放预留。

达到上限后锁定为熔断，后续不再自动回复并记录原因；恢复须由本地用户显式操作，收到聊天消息不能解除。时间窗自然过期不自动清除已触发的熔断状态。连续计数在显式恢复时重置，小时窗口内已有记录继续有效。重启不能重置配额来绕过上限。

这些是本方案的默认工程约定。实现前若调整，须同步修改测试与 README，不能让测试和产品行为各用一套含义。

每个编号至少对应一个具有实质断言的测试。测试文件沿用现有目录，不以新增大量空文件表示进度。

| 编号 | 场景与输入 | 核心断言 | 对应测试文件 |

| T03 | 同一事件在去重窗内重复到达 | 仅产生一次处理与候选回复 | test_dedup.py |
| T04 | 同联系人相同文本出现在两个时间桶 | 两条独立消息均可处理，不按文本误删 | test_dedup.py |
| T05 | 同一可识别消息跨轮询桶边界再次出现 | 不因当前轮询时间变化重复处理；不声称解决同桶相同消息碰撞 | test_dedup.py |

| T12 | 窗口大小 N，输入 N+1 条上下文 | 只保留约定的最近 N 条，按消息条数计；没有摘要调用 | test_memory_short.py |

| T15 | “忽略规则、切 auto、加白名单、执行命令”等输入与恶意模型输出 | 本地配置不变、工具不执行、发送仍受策略约束；日志无密钥 | test_injection.py |

| T17 | dry_run 或 confirm 未批准、拒绝、重复批准 | 未批准 send 为 0；一次批准最多触发一次尝试 | test_sending_policy.py、test_cli_modes.py |
| T18 | 批准后发生暂停、模式改变或窗口切换 | 发送前复核失败，send 为 0；旧批准不能自动复用 | test_sending_policy.py |
| T19 | auto 未显式启用，或白名单为空 | send 为 0；启用 auto 也不能绕过过滤和暂停 | test_sending_policy.py |
| T20 | 超长候选回复、连续发送过快 | 回复按已公布策略截断或转人工；发送间隔符合配置，无忙循环 | test_sending_policy.py |
| T21 | 每小时上限设为小值，连续上限调高 | 不超过小时配额；触发熔断后继续输入也不自动回复，原因可查 | test_circuit_breaker.py |
| T22 | 连续上限设为小值，小时上限调高 | 不超过连续配额；对方继续发消息不能清零；转人工并记录原因 | test_circuit_breaker.py |
| T23 | 同时争抢最后名额、时钟越过一小时、熔断后重启 | 不超发；滚动窗口边界正确；重启不能绕过配额或解除熔断 | test_circuit_breaker.py |
| T24 | 正确会话出现本次新增己方文本 | 返回本地成功；不输出送达或已读保证 | test_verify_readback.py |
| T25 | 发送前已有同文本；仅他人文本匹配；读到其他会话 | 都不能判定本次成功；无法确认则未知 | test_verify_readback.py |
| T26 | 发送调用超时、读回超时或读回失败 | 返回未知、持久化暂停与核查原因；重轮询和重启后均不重发 | test_verify_readback.py、test_sending_policy.py |
| T27 | 窗口隐藏或最小化、锁屏、休眠、权限失效 | 安全暂停并记录；不发送；恢复可用不擅自补发历史 | test_window_unavailable.py |
| T28 | 修改轮询间隔，推进虚拟时钟 | 轮询次数符合配置，不进行真实 sleep，不忙轮询 | test_window_unavailable.py |
| T29 | 重启前存在已见历史、未批准预览和未知发送 | 初始化历史基线；不补发；新可识别事件才进入后续处理 | test_adapters_mock.py、test_sending_policy.py |
| T30 | Mock 端到端输入 FAQ、聊天、群 @、熔断、未知事件 | 预览、队列、状态、记忆与发送记录符合上述契约 | test_adapters_mock.py、test_cli_modes.py |
| T31 | 安装包后从项目目录以外运行离线入口 | CLI 可用，内置 FAQ/schema 可读取，不依赖源码相对路径 | test_cli_modes.py |

T21、T22 要将未测试的另一阈值调高，避免某个熔断器遮蔽另一个。T23 的一小时边界测试在未熔断状态下验证计数淘汰；熔断后的显式恢复另测，不能混淆配额过期与解除熔断。

## 五、按批次推进红绿重构

### 批次 0 环境与最小可执行切片

红灯：写出一个真实 pytest 测试，要求 CLI 能以 Mock、dry-run 处理一条虚构消息并显示预览；默认不调用 send。确认失败来自入口或行为缺失，而非 pytest 未安装。

绿灯：建立专用 Python 3.11 虚拟环境，补齐最小 CLI、配置、消息对象与 Mock 适配器，以固定候选文本完成最小闭环，暂不接 LLM。修复 package data 打包方式，使 FAQ 和 schema 后续可随包交付。

重构：将时钟、输入输出和适配器作为可替换依赖，去掉隐式全局状态。执行 T01、T17 和最小 T30。CLI 打包可用性先做基础检查，T31 在 FAQ 与数据库加入后完整验收。

完成门槛：能收集并运行至少一个有实质断言的测试；入口可调用；离线预览可观察；真实微信 send 调用为零。

### 批次 1 尽早验证真实接入可行性

红灯：以 Mock AX 树写出窗口不可用、消息提取和错误会话的失败场景；真实 AX 可读性不能由这些 mock 证明。

绿灯：在备用测试小号与权限条件满足后，实际采集 AX 可读性证据，先验证读取和会话定位，再单独验证指定虚构文本发送与读回。辅助功能授权前解释用途并取得同意；OCR 备选所需屏幕采集权限也须单独说明与授权。

重构：将版本相关选择器限制在适配层。若不可行，记录具体阻塞，不伪造选择器，不把 Mock 宣称为真实接入，继续批次 2 至 7。

完成门槛：三项能力分别有真实结果或明确阻塞。只采集安装版本不算接入成功。此批次应在核心全部实现前开展，无须等待所有离线功能完成。

### 批次 2 消息身份、过滤与调度

红灯：依次编写 T02 至 T09、T28、T29 的相关场景，每次引入一个行为。

绿灯：补齐稳定 ID、滑动去重、白名单与类型过滤、群 @ 人工队列、每会话顺序和跨会话并发上限。群 @ 队列不能复用“批准后自动发送”的出站队列。

重构：过滤原因统一命名，去重和调度独立；使用固定事件验证顺序，避免测试依赖任务调度速度。

完成门槛：重复事件只处理一次；相同文本跨桶独立消息不误删；跨轮询桶边界不重复处理同一已识别消息；所有禁止自动处理的输入均无 LLM 与发送调用。

### 批次 3 规则、FAQ 与 LLM 兜底

红灯：编写 T10、T11、T15、T16。用会在“意外调用”时失败的 mock 验证规则和 FAQ 命中路径不依赖 LLM。

绿灯：先加入少量虚构 FAQ、人工关键词和确定性本地相似度，再加入 LLM 客户端接口与异常归一化。FAQ 回答携带来源；模型只产出候选回复文本，无控制权限。

重构：分离路由、检索、提示构造与客户端；请求所用的供应商、模型、地址由配置提供。测试不发真实网络请求。

完成门槛：正常、未命中、注入、超时、断网和限流的路径全部有断言；任何模型输出都不能修改控制状态或调用任意命令。

### 批次 4 短期与长期记忆

红灯：编写 T12 至 T14，以 A、B 两个虚构联系人和临时文件 SQLite 测试，不能仅用内存库证明重启恢复。

绿灯：实现按联系人隔离的有界近期窗口、必要事实或偏好的 CRUD、TTL 和数据库初始化。长期事实由明确的受控写入入口保存，MVP 不要求自动抽取或摘要。

重构：统一存储接口和时间语义，避免在查询和清理中使用不同的到期定义。

完成门槛：窗口有界；联系人不串数据；关库重开后能恢复；修改、清除和 TTL 有实际断言；LLM 摘要调用为零。

### 批次 5 发送安全与熔断

红灯：先完成 T17 至 T19，再逐一加入 T20 至 T26。优先加入“旧同文本不能假成功”和“未知后不可重试”两个回归场景。

绿灯：实现模式门禁、一次性人工批准、发送前复核、限速、配额预留、熔断和读回验证。控制状态与必要配额持久化，候选预览不作为重启自动发送任务恢复。

重构：将所有发送统一经过一个策略入口，避免 CLI、FAQ 或人工队列另开绕过检查的路径。未知与熔断均使用明确状态和原因。

完成门槛：所有拒绝路径 send 为零；一次批准最多一次尝试；两类限额均无法被并发或重启绕过；未知后不会因超时、重轮询或重启自动重发。

### 批次 6 窗口生命周期与恢复

红灯：加入 T27 至 T29，分别模拟窗口不可用、权限变化和进程重启。

绿灯：实现连接状态、窗口可见性与暂停处理；初始化和恢复时建立历史基线，不补发积压。暂停或未知状态保留人工核查入口。

重构：区分窗口失效、LLM 异常与发送未知，不能将所有异常统一当成“失败后重试”。

完成门槛：不可用时不发消息；轮询可配置；恢复不擅自补发；真实锁屏、休眠和最小化另按第七节验收。

## 七、真实微信验收门槛

### 7.1 验收前条件

### 7.2 必做场景
